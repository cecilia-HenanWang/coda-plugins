交叉评审的提示词，由 scripts/review.mjs 读取。措辞、要求都可以改；{{…}} 由脚本换成整段文字，没有内容时换成空：

- {{number}}、{{url}}：PR 编号与地址
- {{how}}：去哪里看改动（检出的提交、与目标分支的分叉点、git diff 命令）
- {{guidelines}}：项目评审准则，即 PR base 提交里的 .coda/review.md，没有就空
- {{checks}}：这个提交上各项 GitHub 检查的结论（评审前已等它们都有了结果），没有检查或手动发起时为空
- {{author}}：PR 作者写的标题、分支与正文，包在随机标记之间
- {{previous}}：这条运行上一次评审的发现，请评审方核实是否已解决
- {{focus}}：手动发起时给的关注点
- {{principles}}：设置「评审重点」里勾选的几项，各取 principles/ 下同名文件的一段，都不勾时为空

必须保留的只有最后一段：回复末尾的 review 代码块与它的 JSON 格式，脚本靠它读出结论（severity 只能是 P0 到 P3）。
这段注释不会发给评审方。

请对 PR #{{number}}（{{url}}）做交叉评审。

{{how}}

{{guidelines}}

{{checks}}

{{author}}

{{previous}}

只报可操作的发现，每条都要有证据：行为问题写出可达的触发路径和后果，结构问题写出具体的耦合或理解成本，并给出更简单的改法。只是"可能出错"却没有可达路径的、等价的设计选择、个人风格偏好，不报；没有值得报的就说没有。检查没通过时，先判断是不是这次改动引起的。

{{principles}}

每条标严重程度：P0 阻断（数据丢失、安全问题、主要功能不可用）；P1 严重（严重的行为错误，以及会扩散、难以撤回的问题：别人会照着写、越晚越难改的，不论出在哪方面）；P2 一般（影响有限的缺陷，或局部、容易改回的问题）；P3 低优（可读性、命名、小改进）。

说明哪些部分成立；不要提交或推送，也不要修改工作树以外的任何文件。

{{focus}}

回复的最后，单独给出一个代码块：开头一行是三个反引号加 review，结尾一行是三个反引号，中间是一个 JSON 对象，只有 findings 一个字段，是发现的数组，每条有 severity（P0 到 P3）、title（一句话）、location（文件:行，可空）、detail（问题、触发条件与建议）；没有发现时 findings 是空数组。
